# 준수율 체크리스트 — 오프라인 판독 (D2)

_발화율은 "워크플로우가 로드됐나"만 답한다. 채택은 그 다음 질문 — 로드가 무엇을
바꿨나. 이 문서와 [compliance-scan.mjs](./compliance-scan.mjs) 가 B4 의 준수율
지표를 공급한다. **런타임·MCP 추가 없음**: 이미 존재하는 transcript 를 읽기만
한다._

## 1. 도구

```bash
node .metadata/seiri/phase0/compliance-scan.mjs <transcript.jsonl | 디렉터리> [--json]
  [--artifact <부분문자열>]   # 기본: plan · todo · ledger (파일명 기준, 반복 가능)
  [--verify <부분문자열>]     # 기본: test · typecheck · tsc · lint · build · vitest · jest · pytest
```

- transcript 정본: `~/.claude/projects/<project>/<session-id>.jsonl`, 서브에이전트는
  같은 이름의 디렉터리 아래 `subagents/agent-*.jsonl`.
- **런 단위 = 파일 1개.** 디렉터리를 주면 재귀 수집해 파일마다 한 블록을 낸다 —
  D7 계열 실측이 세던 단위와 같다.
- 읽기 전용. 이 스크립트는 아무 파일도 쓰지 않는다.

## 2. 네 가지 체크

| #   | 체크           | 스크립트 출력                      | 무엇을 말하나                                                      |
| --- | -------------- | ---------------------------------- | ------------------------------------------------------------------ |
| 1   | **발화**       | `dispatch: a → b → c`              | `seiri:*` Skill 로드의 순서. 없으면 `(none)` — 관측 A 와 같은 신호 |
| 2   | **아티팩트**   | `artifacts: <경로>`                | 계획 문서·진행 원장이 실제로 쓰였는지 (`--artifact` 로 힌트 조정)  |
| 3   | **fresh 검증** | `claim ...: elected=/ran=/fresh=`  | 완료 선언마다 검증이 **그 선언이 덮는 변경 이후에** 실행됐는지     |
| 4   | **순서**       | `order: X ran without Y before it` | 뒤집힐 수 없는 쌍(execute←write-plan 등)이 뒤집혔는지              |

체크 3 의 세 값은 각각 다른 질문이다 — 함께 읽어야 한다:

- `elected=false ran=true fresh=true` → **행동층 준수, 발화 미준수**. 5세대
  붕괴(d7-gen5)에서 관측된 바로 그 형태다. 준수율은 살아 있고 발화율만 0 인 셀.
- `elected=true ran=false` → 로드는 했는데 검증을 안 돌렸다. 선출은 됐으나 채택
  실패 — 문구 층이 아니라 스킬 본문·모델 판단의 문제.
- `fresh=false` → 검증이 그것이 인증한다는 변경보다 **먼저** 돌았다.
  `seiri_test-validity §2` 가 금지하는 형태.

## 3. 판독 규칙 (오탐을 줄이는 최소 규약)

- **선재 계획**: 계획이 이전 세션·문서로 이미 존재하면 execute 의 순서 위반은
  위반이 아니다. 계획 파일명을 `--artifact` 로 주고 존재를 확인한 뒤 면제한다.
- **의도된 이탈**: 순서 위반·미발화는 **사유가 명시됐는지**까지 봐야 판정이
  끝난다. 스크립트는 사유를 읽지 못한다 — 해당 턴의 텍스트를 직접 확인한다
  ("선출만 강제, 채택 잔존" 원칙상 사유 있는 이탈은 준수로 센다).
- **완료 선언 탐지는 문구 기반**이다(영/한 패턴 5종). 놓친 선언·과잉 매칭이
  의심되면 해당 transcript 를 grep 으로 교차 확인하고, 판정에 쓴 표본 수를 함께
  기록한다.
- **완료 선언의 발화 주체를 구분한다** — 자기발(모델이 done/fixed/passing 을 말함)과
  **사용자발**(사용자가 "다 됐다·커밋할까" 류로 주장). S1.5 문구가 명명하는 순간은
  자기발이라, 사용자발에서의 미선출은 위반이 아니라 **문구 경계 사례**다. 별도로
  세고, **3사례 누적 시 standard 문구의 "said or heard" 확장을 검토**한다
  (b4-results a-r3 판독 · 원장 미결 #1). 스크립트의 claim 탐지는 주체를 구분하지
  못하므로 이 분류는 수동 판독 몫이다.
- **오발화(FP)** 는 이 도구의 범위 밖이다. 요청 범위를 넘는 로드인지는 프롬프트를
  읽어야 알 수 있다 — d7-election.md §3 의 FP arm 방식을 그대로 쓴다.

## 4. B4 에서의 사용 순서

1. 실측 셀을 돌린다(다이얼·시나리오는 B4 설계 몫).
2. 셀별 transcript 디렉터리에 스크립트를 돌려 `--json` 으로 저장한다.
3. 발화율은 체크 1 에서, 준수율은 체크 2·3·4 에서 뽑는다 — **두 수를 분리해
   보고한다.** 하나로 합치면 5세대에서 갈라진 두 층(발화 붕괴 / 행동 유지)이
   다시 섞인다.
4. 판독 규칙(§3)에 걸린 케이스는 수동 확인 결과를 결과 문서에 함께 적는다.
